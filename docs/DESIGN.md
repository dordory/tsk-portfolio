# territory_cards 앱 설계서

이 문서는 새 Django 앱 **`apps/territory_cards`** 의 설계를 정리한 것이다.
구글시트(구역카드)를 백엔드 데이터소스로 삼아, LINE MINI App(LIFF)에서 봉사구역을
열람·기록하는 웹앱을 기존 TSK 프로젝트에 추가한다.


---

## 1. 무엇을 만드는가 (한 줄 요약)

특정 포맷의 구글시트(구역카드)를 **행 데이터로 읽어 웹뷰로 보여주고**, 화면에서 입력·갱신하면
**해당 구글시트에 즉시 반영**하는 프로그램. 배포 형태는 **LINE MINI App**.

- 사용자: 정해진 소수의 봉사자 (LINE 인증)
- 쓰기 방식: **화면 입력 → 즉시 시트 반영** (시트를 직접 실시간으로 보는 사람이 있기 때문)
- 초기 버전 전제: **시트 양식은 절대 바뀌지 않는다** (좌표 하드코딩 허용)
- 동시 사용자: 최대 10명 미만

### 버전 로드맵 (사용자 명시)
1. **초기 버전(이번 작업)**: 좌표 고정, 구글시트를 직접 읽고 쓴다.
2. 다음 버전: 헤더 자동 탐지 기능 추가.
3. 최종 버전: 구글시트를 버리고 주소(구역) 데이터를 **완전히 DB화**.
   - ⚠️ 이 최종 버전의 DB 스키마는 **이미 `apps/territory` 에 상당 부분 존재**한다(아래 6장 참고).

## 2. 대상 구글시트 구조 분석

### 2-1. 마스터 인덱스 시트 ("시트리스트_시트")
서비스 계정이 접근 가능한 모든 구역카드의 목록. 앱의 **시트 선택 화면**의 데이터 소스.

| 열 | 내용 | 예시 |
|----|------|------|
| A | 구역카드 이름 | `区域09_サンプル会衆(10cards)` |
| B | 시트 URL | `https://docs.google.com/spreadsheets/d/<id>/edit?gid=<gid>#gid=<gid>` |

- 1행은 헤더(`구역카드`, `URL`), 2행부터 데이터.
- 구역카드 이름은 **항상 `...(Ncards)` 패턴** → 정규식 `(\d+)cards` 로 탭 개수 N 파싱.
  - 예: `(10cards)` → 탭 **1~N(=10)** 을 연속 번호로 생성.
  - 실제 시트를 열어 탭을 세지 않아도 되고, 특수 탭(`삭제금지`·`반납할구역`)은 자연히 목록에서 제외됨.

### 2-2. 구역카드 시트 (탭 1~N, 모두 동일 구조)
탭 하나가 세로로 4개 영역으로 나뉜다. **행 형태가 균일하지 않은 이유가 이것.**

| 영역 | 행 | 성격 | 앱에서의 취급 |
|------|-----|------|---------------|
| 제목/헤더 | 1~2 | 병합셀, 구역명·주소안내·"임명받은 전도인" 라벨 | 대부분 읽기 전용 (단, **J2** 는 씀) |
| **데이터 본문** | **3~17** (최대 15행) | 실제 구역 주소 + 방문기록 | 리스트 표시 / 편집 |
| 참고(안내문) | 18~19 | 사용 규칙 텍스트 | 무시 |
| 메모 | 20 | 탭 전체 자유기입 (관리자용) | **무시** |

#### 데이터 본문(3~17행) 컬럼

**왼쪽 — 집/장소 정보 (마스터 데이터, 원칙적으로 읽기 전용)**

| 열 | 내용 | 앱에서 |
|----|------|--------|
| A | 지역명 | **표시 안 함** (관리자용 정보, 전 행 공통) |
| B, C, D | 번지 (일본 주소체계 + 종이관리 습관의 잔재) | **이어붙여 표시** (읽기 전용) |
| E | 건물명 | 표시 (읽기) |
| F | 비고 | **행별 메모로 취급 → 표시 + 편집 가능** |
| G | 전화번호 | 표시 (읽기) |
| H | 지도보기 (하이퍼링크 "지도") | **링크 버튼으로 그대로 표시** (스마트폰에서 구글맵 앱 실행) |
| I | 재방 | (용도 미정 — 필요 시 확인) |

**오른쪽 — 방문 이력**

| 열 | 내용 |
|----|------|
| **J2** | `임명받은 전도인 :` 라벨 셀. 탭 진입 시 여기에 담당자 이름을 쓴다 |
| J ~ O (3행부터) | 방문기록 6칸. 왼→오 순으로 회차가 쌓임 |

#### 방문기록 셀 하나의 구조
- 한 셀에 **줄바꿈으로 3줄**: `상태` / `YY/MM/DD` / `오전(오후) H시`
  - 예: `만남` / `25/02/20` / `오전11`
- **드롭다운(데이터 유효성)은 "상태"만** 선택. **날짜·시간은 상태를 선택한 시점이 자동 입력**.
- 선택 가능한 상태값 목록은 **`삭제금지` 탭**에 들어있다 (앱은 여기서 드롭다운 선택지를 읽어옴).
  - 상태 예: 만남, 부재, 이사, 간격방문, 방문금지, 외국인, 새로발견, 확인필요
- 상태별 셀 배경색이 다름(만남=초록, 부재=노랑, 확인필요=파랑, 외국인=보라 등) — 앱 UI 에도 상태색 반영 권장.

#### 방문기록 추가 로직 (중요)
- J~O 중 빈 칸이 있으면 다음 칸에 기록.
- **6칸이 다 차면**: J(가장 오래된 기록)를 버리고 **K~O 를 왼쪽으로 한 칸씩 시프트**, 비워진 O에 신규 기록.
- "가장 최근 방문" = J~O 중 **가장 오른쪽에 채워진 칸**.

#### 날짜·시간 포맷 / 시간대
- 날짜: `YY/MM/DD`
- 시간: `오전`/`오후` + **시 단위만** (분 없음). 예: `오전11`, `오후01`
- 시간대: **JST 고정** (`settings.TIME_ZONE = 'Asia/Tokyo'` 이미 설정됨).

#### 특수 탭
- `삭제금지`: 상태값 목록 저장소. 봉사자 화면에 노출 안 함.
- `반납할구역`: 관리자용. 무시.

## 3. 사용자 시나리오 (4화면 플로우)

관리자가 봉사자에게 **시트 이름과 탭 번호를 구두/메시지로** 지정해준다. 봉사자는:

1. **인증**: LINE MINI App(LIFF) 접속 → LINE 신원 확인 (기존 `apps/line` 흐름 재사용).
2. **① 시트 목록 화면**: 마스터 인덱스(A열) 기반 구역카드 목록 → 자신에게 지정된 시트 선택.
3. **② 탭(구역) 목록 화면**: 이름에서 파싱한 `1~N` 번호 표시 → 지정된 탭 번호 선택.
   - 이때 해당 탭 **J2** 를 확인:
     - 비어 있으면 → `임명받은 전도인 : <LINE 표시이름>` 으로 기록하고 진입.
     - 이미 다른 사람 이름이 있으면 → **경고 화면**: "이미 다른 사람에게 할당된 카드입니다. 계속하시겠습니까?"
       - [계속] → 내 이름으로 갱신하고 진입.
       - [취소] → 카드(탭) 목록으로 되돌아감.
4. **③ 주소 리스트 화면**: 3~17행의 주소들을 리스트로.
   - 각 항목에 **가장 최근 방문 날짜 + 그때 상태**를 함께 표시(J~O 중 가장 오른쪽 채워진 값).
   - 봉사자는 이 상태를 보고 방문 여부를 판단.
5. **④ 상세 / 방문기록 화면**: 특정 주소 탭 → 진입.
   - 방문 이력 전체(J~O) 열람.
   - **F열 비고(행별 메모)** 열람 + 편집.
   - H열 지도 링크 버튼.
   - **신규 방문 결과 추가 입력** (상태 드롭다운 선택 → 저장 시 날짜·시간 자동, 필요 시 시프트).

### 화면 스케치 (참고)
```
① 시트 목록          ② 탭 목록              ③ 주소 리스트           ④ 상세/기록
┌────────────┐   ┌────────────┐   ┌──────────────┐   ┌──────────────┐
│ 내 구역카드   │   │ 区域09 › 구역  │   │ 区域09 · 구역2 │   │ 1-9-23 아파트   │
│ ▸ 区域09... │   │ [1][2][3]...  │   │ ▸1-9-9 …🟢만남 │   │ 📞  🗺[지도]     │
│ ▸ 区域10... │   │ ...      [10] │   │ ▸1-9-13…🟢만남 │   │ 📝비고 …[편집]   │
└────────────┘   │ (J2확인/경고) │   └──────────────┘   │ ─방문이력─      │
                 └────────────┘                        │ [＋방문결과기록] │
                                                        └──────────────┘
```

## 4. 기존 코드에서 재사용할 것 (다시 만들지 말 것)

아래 파일들에서 파악한 재사용 자산:

| 필요 기능 | 기존 자산 | 위치 |
|-----------|-----------|------|
| LINE 인증(LIFF entry, ID Token 서버검증, 세션로그인) | **완성됨** | `apps/line/{views,services,models,urls,middleware}.py` |
| 로그인 사용자 식별 | `request.user` + `@login_required` | (Django auth, `AUTH_USER_MODEL='member.Member'`) |
| 웹/미니앱 UI 분기 | `request.is_liff` | `apps/line/middleware.py` (`LIFFContextMiddleware`) |
| **J2 에 쓸 담당자 이름** | `LineProfile.display_name` | `apps/line/models.py` |
| JST 시간대 | `TIME_ZONE='Asia/Tokyo'` | `tsk/settings.py` |
| 지도 링크 생성 패턴 | `Territory.map_link()` | `apps/territory/models.py:108` |
| 앱 내 뷰/URL 3분할 관례 | user/admin/manager 분리 | `apps/territory/*` |
| 프론트 베이스(Tailwind CDN + Alpine) | `templates/base_with_tailwind.html` | `templates/` |

### LINE 인증 흐름 요약 (services.py 기준)
- `liff_entry` → 프론트에서 `liff.getIDToken()` → `/liff/login/` 으로 POST.
- `verify_id_token()` 이 `https://api.line.me/oauth2/v2.1/verify` 로 **서버측 검증** (client_id=`LINE_CHANNEL_ID`).
- `get_user_from_line()` 이 `LineProfile.line_user_id`(=payload `sub`)로 `Member` 조회.
  - 있으면 `login()` 후 `LOGIN_REDIRECT_URL` 로.
  - 없으면 온보딩(그룹→멤버 선택)으로.
- `request.session['is_liff']` 로 미니앱/웹 UI 분기.

## 5. 새 앱 `apps/territory_cards` 구현 범위 (진짜 새로 만들 것)

### 5-1. 신규 Python 의존성
- `google-api-python-client`, `google-auth` (Google Sheets API v4, 서비스 계정)
- `requirements.txt` 에 추가.

### 5-2. Google Sheets 접근 계층 (`sheets.py` 등)
- **서비스 계정 자격증명**으로 인증. 키는 코드에 두지 말고 환경변수/파일 경로로 (`.env` + django-environ 관례 따름).
- 대상 시트들을 서비스 계정 이메일에 **공유**해두어야 함(운영 준비 항목).
- 기능:
  - 마스터 인덱스 읽기 → (이름, url) 목록.
  - 이름에서 N 파싱, url 에서 spreadsheetId/gid 추출.
  - 탭 1개의 본문(3~17행), J2, F열, H열 하이퍼링크 읽기.
    - ⚠️ 하이퍼링크·셀 서식은 값 API(`values.get`)로 안 나옴 → `spreadsheets.get` 에 `fields`/`ranges` 지정해 `hyperlink`/`formattedValue` 취득 필요.
  - 상태값 목록(`삭제금지` 탭) 읽기.
  - 쓰기: J2 담당자명, F열 비고, 방문기록 셀(+시프트).

### 5-3. 시트 ↔ 도메인 매핑 (`mapping.py` 등)
- 좌표 상수 정의(초기 버전은 하드코딩): `DATA_ROWS = range(3, 18)`, `VISIT_COLS = ['J','K','L','M','N','O']`, `ASSIGNEE_CELL = 'J2'`, `NOTE_COL='F'`, `MAP_COL='H'`, `PHONE_COL='G'`, `BLDG_COL='E'`, `BANCHI_COLS=['B','C','D']`.
- 방문기록 셀 값 조립/분해(`상태\nYY/MM/DD\n오전H시`), 시프트 로직, 최근값 추출.
- 번지 조립 → 표시 문자열.

### 5-4. 뷰 / URL (user 전용, 4화면)
- `apps/territory` 의 관례를 따라 `user_views.py` + `urls.py`(`app_name='territory_cards'`).
- 모든 뷰 `@login_required`.
- 쓰기 액션(J2/비고/방문기록)은 POST + CSRF(`X-CSRFToken`), fetch 기반 즉시 저장.

### 5-5. 템플릿
- `apps/territory_cards/templates/territory_cards/*`.
- `base_with_tailwind.html` 상속. 모바일 우선(one-column, 큰 터치 타깃), `request.is_liff` 분기.
- 지도 버튼은 LINE 환경에서 `liff.openWindow()` 로 외부 열기.

### 5-6. settings/urls 배선
- `INSTALLED_APPS` 에 `'apps.territory_cards'` 추가.
- `tsk/urls.py` 에 라우트 추가(예: `path('cards/', include('apps.territory_cards.urls', namespace='territory_cards'))`).

## 6. ⚠️ 결정 필요 / 주의 (새 세션에서 먼저 확인)

1. **진입점(로그인 후 리다이렉트)**:
   현재 `LOGIN_REDIRECT_URL = 'territory:user_assigned_territories'`, 온보딩은 `territory:user_groups`.
   새 앱을 봉사자의 기본 첫 화면으로 삼을지, 아니면 별도 URL(`/cards/`)로 병행할지 결정.
   → 기존 DB 기반 화면과 **공존**시킬 것을 권장(초기엔 `/cards/` 로 분리, 리다이렉트는 나중에 정리).

2. **인증 데이터 계층 하이브리드**:
   `apps/line` 로그인은 **Member(DB) 레코드**를 요구한다(LineProfile→Member 매핑).
   새 앱은 구역 데이터를 DB가 아니라 시트에서 읽지만, **봉사자 신원은 여전히 Member 로 온보딩**한다.
   즉 "누구인가"는 DB(Member/LineProfile), "구역 데이터"는 시트 — 하이브리드로 간다.
   J2 에 쓸 이름은 `request.user.line_profile.display_name` (없으면 `Member` 표시값).

3. **기존 `territory`(DB) 앱과의 관계**:
   같은 도메인의 "DB 버전"이 이미 있다. 새 앱은 "시트 버전"이며 **중복 도메인**임을 인지할 것.
   모델 이름 충돌 주의(같은 `Territory` 개념). 새 앱은 가능하면 **모델을 만들지 않고**(시트가 소스),
   꼭 필요하면 사용자↔시트/탭 배정 매핑 정도만 최소한으로.

4. **미해결 사소 항목**:
   - I열("재방")의 정확한 용도 — 필요 시 사용자에게 확인.
   - 방문기록 셀의 실제 줄바꿈 문자 확인(시트에서 `\n` 인지) — 구현 시 실제 셀 덤프로 검증.
   - 상태별 색상 매핑값 — `삭제금지` 탭 또는 실제 셀 서식에서 취득.
